## 2026-11-05 — Verify and document matching pipeline recovery

**Problem:** Direct service tests did not verify delivery across the HTTP API, transactional outbox, BullMQ, and separate worker processes. An acknowledged job lost from Redis also needed a documented operator recovery procedure.

**Outcome:** PR #37 adds ten isolated scenarios using the real API and workers. Coverage includes price-time fills, fees, and participant balances across two workers; completed-job replay; Redis unavailability with API restart; failed enqueue acknowledgement; worker termination before and after commit; transient rollback/retry; exhausted retries releasing BTC/USD reservations; cancellation before delivery; and recovery after confirmed Redis job loss. Fault gates stay inside the disposable database, and worker crash recovery uses real BullMQ leases and stalled-job intervals.

**Decision:** Retain global concurrency of one and the PostgreSQL market lock. Distinguish processor completion from a successful trade: final-attempt rejection can complete a job, while failed rejection or exhausted stalled recovery can leave an order `QUEUED` for operator review. The outbox protects delivery until enqueue acknowledgement; it does not keep a second durable copy of acknowledged Redis jobs.

**Recovery procedure:** Added an idempotent SQL statement that restores at most 100 missing matching intents per batch for reviewed `QUEUED` orders, ordered by sequence. The runbook requires stopping consumers and reviewing retained failed/completed jobs before repair. The statement changes neither balances nor order status; it does not introduce automatic periodic recovery of lost jobs.

**Recorded validation:** The PR description reports Node 22.20.0, **303 database E2E tests across 14 suites**, **413 backend unit tests**, **13 isolated-runner tests**, and **5 security-patch tests** passing, plus lint, TypeScript checks, and backend build. PostgreSQL 17 and Redis 7 were isolated and temporary resources were removed. Backend, frontend, and browser PR checks all concluded `SUCCESS`.

## 2026-11-05 — Verify monetary invariants across operation sequences

**Problem:** Individual matching scenarios did not reconstruct each account across creation, fills, cancellation, rejection, and replay. Global conservation alone could miss a credit sent to the wrong account.

**Outcome:** PR #38 adds an independent `BigInt` ledger oracle using units of `0.00000001`, without production arithmetic or settlement helpers. It reconstructs per-user BTC/USD totals from opening balances and persisted fills, verifies active-order reservations and execution quantities, checks maker/taker fee rates and assets, and verifies global conservation including fees. Sixteen oracle regression checks cover deliberately corrupted snapshots and large-value precision.

**Sequence coverage:** Twenty-two persisted cases cover multiple makers, price improvement, minimum units, rounded fees and dust, large balances, reservation/credit failures, second-fill rollback followed by retry and replay, and cancellation races with both taker sides and both winners. PostgreSQL row locks and observed blockers establish race ordering. Four fixed seeds each run 64 generated steps with invariant checks after every operation, then drain queued orders and cancel active ones until reservations are zero.

**Decision and limits:** Use per-fill integer truncation and per-account accounting as an independent reference. Matching/realtime dispatchers are replaced only to control processing order; transactional writes remain real. Delivery recovery is covered by PR #37's separate pipeline suite. These clean-fixture sequences do not reconcile historical accounts or enumerate every possible schedule and input.

**Recorded validation:** The PR description reports Node 22.20.0, **341 database E2E/oracle tests across 16 suites** and **413 backend unit tests** passing. The **38 focused monetary tests** comprise the 22 persisted cases and 16 oracle checks already included in the database-runner total. The oracle also passed separately without a database, and custom-seed reproduction with `INVARIANT_SEED=0` passed. Lint, TypeScript checking, formatting, and backend build passed. Disposable PostgreSQL 17/Redis 7 resources were removed. Backend, frontend, and browser PR checks all concluded `SUCCESS`.

**References:** [PR #38](https://github.com/VarnerDamascenoJr/exchange-matching/pull/38), [merge commit](https://github.com/VarnerDamascenoJr/exchange-matching/commit/a0ce9643419801d81785002ece4c3666772fc2a6), [PR CI](https://github.com/VarnerDamascenoJr/exchange-matching/actions/runs/42133722800), [monetary invariant equations and seed reproduction](https://github.com/VarnerDamascenoJr/exchange-matching/blob/a0ce9643419801d81785002ece4c3666772fc2a6/docs/monetary-invariants.md).
