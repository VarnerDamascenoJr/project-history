## 2026-11-09 — Preserve valid routes under final-distance constraints

**Problem:** Exact enumeration pruned a prefix when its direct return exceeded `maxRouteDistance`, although a later stop can shorten that return in a non-metric matrix.

**Outcome:** PR #59 validates final route distance and prunes only accumulated travel that already exceeds the bound, including empty routes with nonzero diagonal distance. Updated the mathematical formulation and strategy guarantees with worked examples.

**Reported validation:** **85 tests**, including six new regressions. Two reproductions failed before the fix and passed afterward. Scenario, strategy benchmark, simulation, risk, link, and whitespace checks passed on Node 24.20.0 according to the PR.

**Reference:** [PR #59](https://github.com/VarnerDamascenoJr/OptiFlow/pull/59).

## 2026-11-10 — Integrate the native OR-Tools solver

**Outcome:** PR #60 added CP-SAT through a Python JSON bridge while retaining scenario/route contracts. The small fixture returns **744**, compared with heuristic **792**, with `OPTIMAL` and lower bound 744. Results preserve search status, objective bound, and search duration.

**Guarantees and limits:** Only `OPTIMAL` proves optimality for the represented integer model. `FEASIBLE` preserves a valid plan without that proof. Defaults are 50 orders and 1000 ms search; inputs support up to six significant decimal places and scaled values/horizon bounded by `10^12`. Unsupported input or missing solver execution returns an explicit error rather than silently selecting another strategy. The bridge is synchronous in the API process.

**Reported validation:** **97 tests**, real-solver/API coverage, agreement with enumeration on seven versioned scenarios, Docker execution as an unprivileged user, scenario/benchmark/simulation/risk commands, and whitespace checks.

**Reference:** [PR #60](https://github.com/VarnerDamascenoJr/OptiFlow/pull/60), [solver contract](https://github.com/VarnerDamascenoJr/OptiFlow/blob/b96520fec39e2b865104e45b5c8e6dfeb511c096/docs/or-tools-solver.md).

## 2026-11-12 — Reconstruct solver routes with integer precision

**Problem:** Reconstructing a valid integer-model result with floating-point sums could invent lateness or reject capacity/distance/deadline boundaries.

**Outcome:** PR #61 sends model scales through the Python response and uses integer reconstruction/validation before converting to public units. This removes the fixed `1e-8` tolerance while preserving strict detection of real violations. Node and Python bridge updates form one compatible internal change.

**Reported validation:** **102 tests**, including five regressions covering deadline, penalty, distance, capacity, and a real `0.000001`-minute violation, plus the normal scenario/benchmark/simulation/risk commands.

**Reference:** [PR #61](https://github.com/VarnerDamascenoJr/OptiFlow/pull/61).

## 2026-11-12 — Add demand forecasting with temporal evaluation

**Outcome:** PR #62 added last-observation and moving-average forecasts per location/window, complete UTC-window validation, rolling-origin evaluation, MAE/RMSE/bias, and a CLI. Only past observations enter each forecast; selection uses unrounded errors.

**Evidence and limits:** The synthetic alternating series favors moving average with MAE **5 versus 10**; the increasing series favors the naive baseline with MAE **2 versus 3**. These are point forecasts. Selecting the model on the same validation period does not independently measure the future selection process. Forecasts remain inspectable and do not create or overwrite confirmed solver orders.

**Reported validation:** **116 tests**, including 14 new cases, text/JSON/direct CLI execution, and existing solver/simulation/risk checks.

**Reference:** [PR #62](https://github.com/VarnerDamascenoJr/OptiFlow/pull/62), [forecasting assumptions](https://github.com/VarnerDamascenoJr/OptiFlow/blob/b96520fec39e2b865104e45b5c8e6dfeb511c096/docs/demand-forecasting.md).

## 2026-11-13 — Replace the manual router with a modular NestJS backend

**Outcome:** PR #63 introduced NestJS scenario/run/operations modules and application-scoped repository/queue providers while preserving HTTP routes, status/envelope contracts, metrics, and the local console. The JavaScript optimization domain remains separate. TypeScript build hooks, graceful queue draining, and a production Docker build accompany the migration.

**Runtime limits:** History remains local JSON with one writer, and jobs remain in memory. The solver still executes synchronously in the Node API process; the concurrency setting creates no worker isolation. Queue duration checks do not provide general preemptive cancellation. Database-backed storage, durable jobs, and separate workers remain future architecture work.

**Reported validation:** **121 passing tests**, production Docker build, HTTP/container smoke for UI, health, scenarios, an OR-Tools run, and metrics. The container solver returned `OPTIMAL` at cost **744**. `npm audit --omit=dev` reported no vulnerabilities for that dated production dependency set. Both the PR check and main CI succeeded; this is not a new audit performed by this history import.

**References:** [PR #63](https://github.com/VarnerDamascenoJr/OptiFlow/pull/63), [`b96520f`](https://github.com/VarnerDamascenoJr/OptiFlow/commit/b96520fec39e2b865104e45b5c8e6dfeb511c096), [PR CI](https://github.com/VarnerDamascenoJr/OptiFlow/actions/runs/43514509226), [main CI](https://github.com/VarnerDamascenoJr/OptiFlow/actions/runs/43514985168), [runtime and migration boundaries](https://github.com/VarnerDamascenoJr/OptiFlow/blob/b96520fec39e2b865104e45b5c8e6dfeb511c096/docs/backend-architecture.md).
